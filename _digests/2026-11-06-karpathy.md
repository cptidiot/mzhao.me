    summary: |
      **核心论点**

      - MenuGen 是 Karpathy 第一个端到端 vibe coding 的应用：拍下餐厅菜单，为每道菜生成图片，解决看不懂菜单的痛点——Pâté、Tagine、Cavatappi，以及 "Confit tubers folded with matured curd" 这类天书菜名。
      - 他几乎没有 web 开发经验，100% 的代码由 Cursor + Claude 写成；从 hackathon 本地原型一路做到部署、登录、付费的真实产品，还能赚 10% 的差价。

      **本地原型快，部署才是硬仗**

      - 第一个本地版极快：Cursor + Claude 3.7 迅速写出 React 前端，页面漂亮、动画流畅、响应式齐全——当时感觉完成了 80%，实际只有 20%。
      - OpenAI API（OCR 菜单）与 Replicate API（生成菜品图）：开 key 的菜单层层嵌套、要选 "projects" 和权限；Claude 不断幻觉出已废弃的 API 与模型名，靠来回粘贴官方文档才修好；Replicate 的官方文档本身也略滞后（返回的是 Streaming 对象而非 JSON）；两边都撞上限流，调试极难——事后得知这是服务商的反欺诈保护，但也确实拦住了合法新用户。
      - Vercel 部署：本地能跑、线上构建却因 lint 错误（未使用变量）失败，只能靠推假调试 commit 反复触发部署来排错；更大的坑是 .env.local 在 .gitignore 里，API key 根本没进仓库，得手动去 Vercel 设置里补；更意外的是，私有仓库竟被自动部署到一个公开可猜的 URL 上。
      - Clerk 登录：Claude 幻觉出约 1000 行已废弃的 Clerk API 代码，又是一轮粘贴文档；切生产环境还强制要求自有域名，于是买下 menugen.app、改 DNS、再去 Google Cloud Console 配 OAuth、等审批，在三套设置里来回折腾，一度想放弃。
      - Stripe 付款：官方给的是 JavaScript 示例，他的项目是 TypeScript，粘贴就报 lint 错；还要在后台建 Product、建 Price、区分 price key 与 product key、四处复制密钥；更关键的是他发现 Claude 用邮箱匹配付款和用户积分的设计是错的（结账邮箱未必等于注册邮箱），指出后 Claude 立刻道歉并改成用唯一 user id 传 metadata——他调侃这就是 "gaslighting"。
      - 数据库与任务队列至今没做：所有处理都是即时请求、无缓存无保存，菜单太长就超时、刷新页面结果全丢；正确做法应是 Supabase PostgreSQL + Upstash 队列，但那意味着更多服务、更多账号、更多配置——"Too much bear"，留作以后。

      **TL;DR 与展望**

      - 本地 demo 令人振奋，做成真实部署应用却是一场痛苦的 slog：现代应用像组装 IKEA 未来——服务、文档、API key、配置、开发/生产环境、限流、定价层级……而 LLM 的知识总有点过时，还会犯微妙的设计错误、幻觉、"gaslight"。
      - 最耐人寻味的一点：他大部分时间根本没花在代码编辑器里，而是在浏览器标签页之间跳转、做各种设置和胶水工作——而这些工作 LLM 根本接触不到、也操作不了。"我们 2027 年要这样自动化整个社会？"
      - 他的药方有三条：出现一个"电池全配"的开发平台（Vercel Marketplace 的反面：域名、托管、登录、支付、数据库、server functions 开箱即用）；各服务变得对 LLM 友好（CLI、curl 可配置、Markdown 文档——直接对 LLM 说话，别对开发者说话）；以及反思：MenuGen 也许根本不该是个完整应用——一次 GPT 调用 OCR 菜单、再循环生成图片并排版展示就够了，像一个 custom GPT 或 Artifact 那样。
      - 结论：今天用 vibe coding 做完整 web 应用还很 messy，不适合真正重要的事，但伟大的苗头已经清晰可见；做应用的门槛正跌向约等于零，超个性化的自动化会成为人类创造力的新画布。
