    summary: |
      **核心论点**

      - 这是 Karpathy 在 Sequoia Ascent 2026 与 Sequoia 合伙人 Stephanie Zhan 的炉边谈话。文中说明：他把自己的博客与推文喂给 LLM（Codex 5.5），由其根据谈话 transcript 生成了这份总结与清理版实录——以下即该总结的核心内容。
      - 总判断：LLM 不再只是聊天机器人或自动补全，而正在成为数字工作的新可编程层。稀缺的东西正在转移：代码生成、API 记忆、样板代码、初稿、重复配置、简单转换越来越不稀缺；理解、品味、eval 设计、安全、系统边界、agent 编排、领域反馈回路，以及判断模型何时"跑偏"，越来越稀缺。

      **1. 2025 年 12 月是 agent 拐点**

      - 他最近说自己"从未感觉作为程序员如此落后"。原因不是编程本身变难，而是默认工作流变了。2025 年大部分时间里，Claude Code、Codex 等 agent 有用，但仍需频繁纠错；2025 年 12 月前后出现台阶式变化：生成的代码块变大、更连贯、更可靠，他开始信任 agent 承担更多工作。
      - 编程的单位从"敲一行行代码"变成委派"宏操作"：实现这个功能、重构这个子系统、调研这个库、搭这个服务、写测试并跑通修复、比较方案并提出计划。程序员正被重构为 agent 的 orchestrator（编排者）。

      **2. Software 3.0：context window 是新的程序**

      - 他把软件史排成一个序列：Software 1.0 是人写显式代码；Software 2.0 是人造数据集、目标与神经网络，程序被学进权重；Software 3.0 是人通过 prompt、context、工具、示例、记忆与指令来编程 LLM，context window 成为主杠杆，LLM 是其上的解释器，在数字信息空间里做计算。
      - 例证是安装：旧世界里，在众多环境上装一个复杂工具需要写满条件分支的脆弱 shell 脚本；Software 3.0 世界里，安装程序可以是一段粘贴给 agent 的文字——agent 自己读本地环境、调试报错、适配机器、完成安装。这是一种不同的程序：没那么精确，但更自适应。

      **3. MenuGen 与软件消失**

      - MenuGen 是他的例子：传统 web app——拍餐厅菜单照片、OCR 菜名、生成菜图、在 UI 里渲染结果，需要前端代码、API、图像生成、部署、auth、支付、密钥与基础设施。
      - 但后来他看到了 Software 3.0 版：拍下菜单照片，交给多模态模型，让它把菜图直接渲染到菜单图片的像素上。那个版本里，大部分 app 消失了——神经网络直接把输入媒体变换成输出媒体，旧软件栈只是围绕这个变换搭的脚手架。
      - 对创始人的启示：AI 不只是更快地造旧 app，有些 app 根本不该以 app 形式存在。

      **4. 机会不止于更快编程**

      - 变化不止于写代码。LLM 让过去不可编程的信息处理变得可编程。他的 LLM Wiki 是最清楚的例子：agent 不再每次用 RAG 从原始文档里回答问题，而是把原始来源持续编译成一个持久的 Markdown wiki——摘要、实体页、概念页、矛盾点、交叉链接、日志与不断演进的综合。
      - 没有古典程序能稳健地在杂乱的人类文档之上维护这种知识库，但 LLM 可以。教训：别只问"现有工作流能被 AI 加速多少"，也要问"什么信息转换以前不可能、现在自然了"。

      **5. 可验证性（verifiability）解释 AI 在哪跑得最快**

      - 他的核心自动化框架：传统软件自动化"可指定"的事；LLM 与强化学习自动化"可验证"的事。如果一个任务有自动奖励或成功信号，模型就能练它——数学、代码、测试、benchmark、游戏与许多工程任务进步如此之快，正因为它们可重置、可重复、可奖励。
      - 这也解释了为什么代码 agent 感觉比普通聊天机器人好得多：代码给模型反馈——测试通过或失败、程序跑通或崩溃、diff 可以检查、benchmark 可以测量。

      **6. Jagged intelligence 有两轴：可验证性与训练重视程度**

      - 访谈给可验证性论点加了一个重要修正：模型能力不只取决于任务是否可验证，还取决于实验室在训练、后训练、合成数据生成与强化学习里是否重视该任务。粗略公式：capability spike ≈ verifiability × training attention × data coverage × economic value（能力峰值 ≈ 可验证性 × 训练注意力 × 数据覆盖 × 经济价值）。
      - 国际象棋是好例子：GPT-4 下棋变好，未必是通用智能平滑提升，也可能是训练集里加了大量棋谱。前沿模型没有附带说明书——它们是预训练混合、RL 环境、benchmark 压力、产品优先级与经济激励的产物，在某些地方尖峰突起，在另一些地方表现怪异。
      - 对创始人的实际问题是：你的任务在模型的"轨道"上吗？如果在可验证且被重点训练的区域，模型可能飞起来；如果不在，它可能在出人意料的基础地方失败，你需要更好的 context、工具、微调、自己的 eval 或自己的 RL 环境。

      **7. Vibe coding vs. agentic engineering**

      - 他区分两个相关但不同的概念：vibe coding 抬高下限，让几乎任何人通过描述想要什么来创造软件；agentic engineering 抬高上限，是协调易错 agent 同时保住正确性、安全、品味与可维护性的专业 discipline。
      - Vibe coding 适合原型与个人工具，严肃团队需要的是 agentic engineering。Agentic engineer 不盲目接受生成的代码：设计 spec、监督计划、检查 diff、写测试、建立评估循环、管理权限、隔离 worktree、保住质量。
      - MenuGen 的支付 bug 是好例子：agent 试图用邮箱地址把 Stripe 购买匹配到 Google 账号——代码看起来合理，但系统设计很糟，因为 Stripe 邮箱与 Google 登录邮箱可能不同。人需要足够的产品与工程判断，坚持用持久的 user ID。
      - 前沿技能不是背 API 细节——agent 能记住某个张量库用 `dim`、`axis`、`keepdim`、`reshape` 还是 `permute`；人仍需理解底层概念：存储、view、内存拷贝、不变量、身份、安全边界与系统形态。

      **8. 招聘应该改变**

      - 如果 agentic engineering 是新的专业技能，招聘应该直接测试它。传统算法题越来越失配。更好的面试可能是：用 agent 做一个大项目、部署它、加固它，然后让对抗 agent 试着攻破它。
      - 这测试的是真实技能：能否为 agent 分解工作、能否写有用的 spec、能否在快速推进时保住质量、能否评审生成的工作、能否加固系统、能否把 agent 当杠杆而不是产出 slop。旧的"10x 工程师"概念可能变得远不止 10x——掌握 agentic 工作流的人可能比别人强出远不止十倍。

      **9. 创始人应寻找有价值的可验证环境**

      - 对创始人来说，一个重要机会是找到有价值、可验证、但前沿实验室尚未重点训练的领域。如果你能创建一个领域专属环境，让模型在其中尝试行动并获得可靠奖励，就可能用微调或强化学习提升性能，哪怕基础模型在那里本来并不出色。
      - 最明显的领域（代码、数学）已被实验室重兵投入，但许多经济上重要的领域可能存在尚未被开发的潜在可验证结构——那就是创业楔子。

      **10. Agent-native 基础设施：为 agent 而建，不只为人**

      - 多数软件仍为人类点击屏幕而建。文档写着"去这个 URL、点这个按钮、打开设置面板"，但越来越多时候，用户不是直接操作的人类，而是人类的 agent。
      - 产品需要 agent-native 的接口：Markdown 文档、CLI、API、MCP server、结构化日志、机器可读的 schema、可粘贴的 agent 指令、安全权限、可审计操作、无头（headless）配置流程。
      - 他用 sensor（传感器）与 actuator（执行器）来思考：sensor 把世界状态变成数字信息，actuator 让 agent 改变世界。未来的技术栈是 agent 代表人与组织使用 sensor 与 actuator。
      - MenuGen 的部署故事仍是好基准：写 app 很容易，难的是接 Vercel、auth、支付、DNS、密钥与生产配置。在成熟的 agent-native 世界里，他应该能说一句"build MenuGen"，agent 就把整个东西部署好，不用他手动点击。

      **11. Ghosts, not animals**

      - 他的 Animals vs. Ghosts 框架是为了避免错误的直觉：LLM 不是动物，没有生物驱动、具身生存压力、好奇心、玩耍或动物意义上的内在动机；它们是人类 artifacts 的统计模拟，由 pretraining、post-training、RL、产品反馈与经济激励塑造。
      - 这很重要，因为拟人化预期会误导人：这些系统可能一刻极其聪明，下一刻又怪异地愚蠢；它们不是平滑的人类心智，而是锯齿状的、异类的工具。正确的姿态既不是轻视，也不是盲信，而是实证熟悉：学会它们在哪行、在哪失败、被训练成什么样，以及如何围绕它们建 guardrail。

      **12. 教育：你可以外包思考，但不能外包理解**

      - 谈话以教育收尾，他反复引用一句话："You can outsource your thinking, but you can't outsource your understanding."（你可以外包思考，但不能外包理解。）即使 agent 做更多工作，人仍需理解来指挥它们——知道什么值得造、什么问题重要、什么结果可疑、什么权衡可接受。
      - 这也是他对 LLM 知识库感兴趣的原因：它们不只是答题机，而是把信息转化为理解的工具。这也关联他的 microGPT 项目——一个单文件、无依赖的完整 GPT 训练与推理实现：教育 artifact 小到人与 agent 都能检查，人类专家贡献提炼后的 artifact 与背后的品味，agent 再向每个学习者交互式讲解。

      **Takeaway**

      - 别只把 AI 当加速器。先问三个问题：你的任务在模型的"轨道"上吗（可验证、被重点训练）？你做的软件会不会被一次模型调用取代？有没有可验证、但没人建 RL 环境的领域值得你去占？
      - 而人的稀缺价值正转向理解、品味、eval 设计、安全、系统边界与 agent 编排——代码生成、API 记忆与样板代码正在变得不稀缺。判断模型何时"跑偏"、保住质量与品味，仍是人的工作。

**10. Agent-native 基础设施：为 agent 而建，不只为人**

- 多数软件仍为人类点击屏幕而建。文档写着"去这个 URL、点这个按钮、打开设置面板"，但越来越多时候，用户不是直接操作的人类，而是人类的 agent。
- 产品需要 agent-native 的接口：Markdown 文档、CLI、API、MCP server、结构化日志、机器可读的 schema、可粘贴的 agent 指令、安全权限、可审计操作、无头（headless）配置流程。
- 他用 sensor（传感器）与 actuator（执行器）来思考：sensor 把世界状态变成数字信息，actuator 让 agent 改变世界。未来的技术栈是 agent 代表人与组织使用 sensor 与 actuator。
- MenuGen 的部署故事仍是好基准：写 app 很容易，难的是接 Vercel、auth、支付、DNS、密钥与生产配置。在成熟的 agent-native 世界里，他应该能说一句"build MenuGen"，agent 就把整个东西部署好，不用他手动点击。

**11. Ghosts, not animals**

- 他的 Animals vs. Ghosts 框架是为了避免错误的直觉：LLM 不是动物，没有生物驱动、具身生存压力、好奇心、玩耍或动物意义上的内在动机；它们是人类 artifacts 的统计模拟，由 pretraining、post-training、RL、产品反馈与经济激励塑造。
- 这很重要，因为拟人化预期会误导人：这些系统可能一刻极其聪明，下一刻又怪异地愚蠢；它们不是平滑的人类心智，而是锯齿状的、异类的工具。正确的姿态既不是轻视，也不是盲信，而是实证熟悉：学会它们在哪行、在哪失败、被训练成什么样，以及如何围绕它们建 guardrail。

**12. 教育：你可以外包思考，但不能外包理解**

- 谈话以教育收尾，他反复引用一句话："You can outsource your thinking, but you can't outsource your understanding."（你可以外包思考，但不能外包理解。）即使 agent 做更多工作，人仍需理解来指挥它们——知道什么值得造、什么问题重要、什么结果可疑、什么权衡可接受。
- 这也是他对 LLM 知识库感兴趣的原因：它们不只是答题机，而是把信息转化为理解的工具。这也关联他的 microGPT 项目——一个单文件、无依赖的完整 GPT 训练与推理实现：教育 artifact 小到人与 agent 都能检查，人类专家贡献提炼后的 artifact 与背后的品味，agent 再向每个学习者交互式讲解。

**Takeaway**

- 别只把 AI 当加速器。先问三个问题：你的任务在模型的"轨道"上吗（可验证、被重点训练）？你做的软件会不会被一次模型调用取代？有没有可验证、但没人建 RL 环境的领域值得你去占？
- 而人的稀缺价值正转向理解、品味、eval 设计、安全、系统边界与 agent 编排——代码生成、API 记忆与样板代码正在变得不稀缺。判断模型何时"跑偏"、保住质量与品味，仍是人的工作。
